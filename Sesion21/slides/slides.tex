Al finalizar, podrás elegir entre dos \textbf{flujos de modelado}: diseñar sin haber definido el gestor, con \textbf{DBML} u otra herramienta, o diseñar sabiendo el gestor desde el inicio, directamente en \textbf{SQL}. \seccion{Flujo A}
\begin{frame}{Flujo A: el gestor todavía no está definido}
\begin{columns}[T,onlytextwidth]
\column{.48\textwidth}
\small\textbf{¿Cuándo pasa?}
\vspace{0.1cm}
\begin{itemize}\setlength\itemsep{5pt}
  \item El cliente aún no decide si usará MySQL, SQL Server u otro gestor.
  \item El diseño se revisa con personas que \textbf{no programan}.
  \item El mismo diseño podría terminar en \textbf{más de un} gestor.
\end{itemize}
\column{.48\textwidth}
\small\textbf{Cómo se trabaja}
\vspace{0.1cm}
\begin{itemize}\setlength\itemsep{5pt}
  \item Conceptual y lógico en una herramienta \textbf{neutral}.
  \item Al final se elige el gestor y se \textbf{genera} el SQL del físico.
  \item Proyecto: \texttt{proyecto\_mascotas\_flujo\_sin\_gestor/}.
\end{itemize}
\end{columns}
\vspace{0.35cm}
\concepto{DBML: Database Markup Language}{\small Un lenguaje de \textbf{texto} para describir tablas y relaciones. \textbf{dbdiagram.io} lo dibuja como diagrama y lo exporta a SQL de MySQL, PostgreSQL, SQL Server u Oracle. Otras opciones: \textbf{Mermaid}, \textbf{ERDPlus} o \textbf{draw.io}.}
\end{frame}
% ---------------------------------------------------------------------
\begin{frame}{Flujo A: así se ve el conceptual en DBML}
\begin{columns}[c,onlytextwidth]
\column{.47\textwidth}
\begin{sqlcode}[\dimexpr\textwidth-2\fboxsep\relax]
\scriptsize
\kw{Table} cliente \{\\
\ind id integer [pk]\\
\ind nombre varchar(255)\\
\ind telefono varchar(255)\\
\}\\[4pt]
\kw{Table} mascota \{\\
\ind id integer [pk]\\
\ind nombre varchar(255)\\
\ind especie varchar(255)\\
\ind raza varchar(255)\\
\ind cliente\_id integer [not null]\\
\}\\[4pt]
\dcom{@relation-meta}\\
\dcom{sourceLabel=\dq{}es dueño de\dq}\\
\dcom{targetLabel=\dq{}pertenece a\dq}\\
\kw{Ref}: cliente.id < mascota.cliente\_id
\end{sqlcode}
\column{.49\textwidth}
\small
\begin{itemize}\setlength\itemsep{7pt}
  \item Cada \textbf{entidad} es un \texttt{Table} con sus \textbf{atributos}.
  \item La \textbf{relación} es un \texttt{Ref}. El \texttt{<} se lee «uno a muchos».
  \item Los \textbf{verbos} de la relación quedan en comentarios.
  \item \texttt{varchar(255)} es solo \textbf{de relleno}: DBML exige un tipo, pero aquí todavía no se decide.
\end{itemize}
\vspace{0.15cm}
\footnotesize\color{utpGris} Archivo: \texttt{2\_modelo\_conceptual.dbml}
\end{columns}
\end{frame}
% ---------------------------------------------------------------------
\begin{frame}{El mismo conceptual en Mermaid}
\begin{columns}[c,onlytextwidth]
\column{.52\textwidth}
\begin{sqlcode}[\dimexpr\textwidth-2\fboxsep\relax]
\scriptsize
\kw{erDiagram}\\
\ind CLIENTE \ ||--|\{ MASCOTA : \dq{}es dueño de\dq\\
\ind MASCOTA \ ||--|\{ CITA \ \ \ : \dq{}tiene\dq\\
\ind SERVICIO ||--o\{ CITA \ \ \ : \dq{}se presta en\dq\\
\ind EMPLEADO ||--o\{ CITA \ \ \ : \dq{}atiende\dq\\
\ind CITA \ \ \ \ ||--o| PAGO \ \ \ : \dq{}se paga con\dq
\end{sqlcode}
\column{.44\textwidth}
\small
\begin{itemize}\setlength\itemsep{7pt}
  \item Solo \textbf{entidades}, \textbf{relaciones} y sus \textbf{verbos}: no pide claves ni tipos.
  \item Los símbolos son la \textbf{pata de gallo}: \texttt{||} es «uno», \texttt{|\{} es «uno o muchos», \texttt{o\{} es «cero o muchos» y \texttt{o|} es «cero o uno».
\end{itemize}
\end{columns}
\vspace{0.2cm}
\small Se lee: \texttt{CLIENTE ||--|\{ MASCOTA} $\rightarrow$ «un cliente es dueño de \textbf{una o muchas} mascotas; cada mascota es de \textbf{un} cliente».
\vspace{0.2cm}
\analogia{Mermaid sirve para \textbf{conversar} el conceptual. Para el lógico conviene DBML: allí ya se escriben PK, FK y reglas que luego se convierten en SQL.}
\end{frame}

\begin{frame}{Flujo A: así se ve el lógico en DBML}
\begin{columns}[c,onlytextwidth]
\column{.55\textwidth}
\begin{sqlcode}[\dimexpr\textwidth-2\fboxsep\relax]
\scriptsize
\kw{Table} cita \{\\
\ind id integer [\nuevo{pk, increment}]\\
\ind fecha\_hora \nuevo{datetime} [\nuevo{not null}]\\
\ind estado \nuevo{varchar(20)} [not null, \nuevo{default: 'programada'},\\
\ind\ind \nuevo{check: `estado IN ('programada',}\\
\ind\ind \nuevo{\hspace*{4.4em}'completada', 'cancelada')`}]\\
\ind mascota\_id \ integer [not null]\\
\ind servicio\_id integer [not null]\\
\ind empleado\_id integer [not null]\\
\ind \kw{indexes} \{ \nuevo{(empleado\_id, fecha\_hora) [unique]} \}\\
\}\\[4pt]
\kw{Ref}: mascota.id \ < cita.mascota\_id\\
\kw{Ref}: servicio.id < cita.servicio\_id\\
\kw{Ref}: empleado.id < cita.empleado\_id
\end{sqlcode}
\column{.41\textwidth}
\small
\begin{itemize}\setlength\itemsep{6pt}
  \item Se agregan \textbf{tipos}, \textbf{PK}, obligatorios, valores por defecto y reglas.
  \item Cada \texttt{Ref} se convertirá en una \textbf{FK}.
  \item \textbf{Sin nada propio de un gestor}: tipos comunes y reglas que cualquiera entiende.
\end{itemize}
\vspace{0.15cm}
\footnotesize\color{utpGris} Archivo: \texttt{3\_modelo\_logico.dbml}
\end{columns}
\vspace{0.2cm}
\ojo{El lógico de la sesión anterior usaba \texttt{typeof()} y \texttt{COLLATE NOCASE}: eso es \textbf{de SQLite}. En el flujo A se deja para el físico.}
\end{frame}

\begin{frame}{Flujo A: recién al final se elige el gestor}
\small Desde el mismo \texttt{3\_modelo\_logico.dbml} se genera el SQL de cada gestor:
\vspace{0.2cm}
\begin{columns}[T,onlytextwidth]
\column{.49\textwidth}
\centering\etiqueta{MySQL}\\[-2pt]
\begin{sqlcode}[\dimexpr\textwidth-2\fboxsep\relax]
\scriptsize
\kw{CREATE TABLE} `cliente` (\\
\ind `id` integer \kw{PRIMARY KEY} \nuevo{AUTO\_INCREMENT},\\
\ind `nombre` varchar(100) \kw{NOT NULL},\\
\ind `telefono` varchar(20) \kw{UNIQUE}\\
);
\end{sqlcode}
\column{.49\textwidth}
\centering\etiqueta{SQL Server}\\[-2pt]
\begin{sqlcode}[\dimexpr\textwidth-2\fboxsep\relax]
\scriptsize
\kw{CREATE TABLE} [cliente] (\\
\ind [id] integer \kw{PRIMARY KEY} \nuevo{IDENTITY(1, 1)},\\
\ind [nombre] varchar(100) \kw{NOT NULL},\\
\ind [telefono] varchar(20) \kw{UNIQUE}\\
)\\
\nuevo{GO}
\end{sqlcode}
\end{columns}
\vspace{0.1cm}
\begin{itemize}\setlength\itemsep{4pt}
  \item Un \textbf{mismo lógico}, dos físicos: cambian la numeración del \texttt{id}, las comillas y los separadores.
  \item Generados: \texttt{4\_modelo\_fisico\_mysql.sql} y \texttt{4\_modelo\_fisico\_sqlserver.sql}, en la carpeta \texttt{modelado/} del proyecto.
\end{itemize}
\end{frame}
% ---------------------------------------------------------------------
\begin{frame}{Flujo A: el SQL generado se revisa}
\small El generador traduce la sintaxis, pero \textbf{no conoce el negocio}. Antes de ejecutar el físico, se revisa:
\vspace{0.2cm}
\begin{itemize}\setlength\itemsep{8pt}
  \item \textbf{Nulos en columnas únicas.} En SQL Server, \texttt{telefono UNIQUE} acepta \textbf{un solo} \texttt{NULL}: el segundo cliente sin teléfono sería rechazado. MySQL y SQLite aceptan varios.
  \item \textbf{Mayúsculas.} Si \texttt{'Corte'} y \texttt{'corte'} deben ser el mismo servicio, depende de la \textbf{intercalación} (\textit{collation}) que use cada gestor.
  \item \textbf{Gestores no incluidos.} \texttt{dbml2sql} no genera SQL de \textbf{SQLite}: \texttt{4\_modelo\_fisico\_sqlite.sql} se escribe a mano.
\end{itemize}
\vspace{0.25cm}
\concepto{Idea clave del flujo A}{\small Conceptual y lógico \textbf{se escriben una sola vez}. Por cada gestor se genera y se revisa un físico distinto.}
\note{SQL Server: los índices y restricciones UNIQUE tratan los NULL como iguales, por lo que solo se permite un NULL; se resuelve con un índice filtrado (WHERE telefono IS NOT NULL). Fuente: https://learn.microsoft.com/en-us/sql/relational-databases/tables/create-unique-constraints}
\end{frame}

\seccion{Flujo B}
\begin{frame}{Flujo B: el gestor se conoce desde el inicio}
\begin{columns}[T,onlytextwidth]
\column{.48\textwidth}
\small\textbf{¿Cuándo pasa?}
\vspace{0.1cm}
\begin{itemize}\setlength\itemsep{5pt}
  \item La empresa ya trabaja con \textbf{un} gestor.
  \item La peluquería contrató un hosting que trae \textbf{MySQL}.
  \item El equipo prefiere escribir \textbf{SQL} desde el principio.
\end{itemize}
\column{.48\textwidth}
\small\textbf{Cómo se trabaja}
\vspace{0.1cm}
\begin{itemize}\setlength\itemsep{5pt}
  \item Los tres modelos se escriben en archivos \texttt{.sql}.
  \item El lógico ya se puede \textbf{ejecutar} y probar en el gestor.
  \item Proyecto: \texttt{proyecto\_mascotas\_flujo\_con\_gestor/}.
\end{itemize}
\end{columns}
\vspace{0.35cm}
\concepto{SQL como lenguaje de modelado}{\small El diseño vive en el mismo lenguaje que crea la base. \textbf{MySQL Workbench} lo muestra como diagrama EER, ya atado a MySQL.}
\end{frame}
% ---------------------------------------------------------------------
\begin{frame}{Flujo B: así se ve el conceptual en SQL}
\begin{columns}[c,onlytextwidth]
\column{.58\textwidth}
\begin{sqlcode}[\dimexpr\textwidth-2\fboxsep\relax]
\scriptsize
\com{ENTIDADES Y ATRIBUTOS}\\
\com{\ \ cliente \ : nombre, teléfono}\\
\com{\ \ mascota \ : nombre, especie, raza}\\
\com{\ \ cita \ \ \ \ : fecha y hora, estado}\\
\com{\ \ \ldots}\\[4pt]
\com{RELACIONES}\\
\com{\ \ cliente \ 1 - N \ mascota \ es dueño de}\\
\com{\ \ mascota \ 1 - N \ cita \ \ \ \ tiene}\\
\com{\ \ empleado 1 - N \ cita \ \ \ \ atiende}\\
\com{\ \ cita \ \ \ \ 1 - 1 \ pago \ \ \ \ se paga con}\\[4pt]
\com{REGLAS DEL NEGOCIO}\\
\com{\ \ Un empleado no atiende dos citas}\\
\com{\ \ a la misma hora.}
\end{sqlcode}
\column{.38\textwidth}
\small
\begin{itemize}\setlength\itemsep{7pt}
  \item Son solo \textbf{comentarios}: el gestor no ejecuta nada.
  \item Dicen \textbf{qué} se guarda y \textbf{cómo} se relaciona, igual que el diagrama del flujo A.
  \item Quedan al inicio del archivo, \textbf{junto al SQL} que vendrá después.
\end{itemize}
\vspace{0.15cm}
\footnotesize\color{utpGris} Archivo: \texttt{2\_modelo\_conceptual.sql}
\end{columns}
\end{frame}

\begin{frame}{Flujo B: así se ve el lógico en SQL}
\begin{columns}[c,onlytextwidth]
\column{.56\textwidth}
\begin{sqlcode}[\dimexpr\textwidth-2\fboxsep\relax]
\scriptsize
\kw{CREATE TABLE} servicio (\\
\ind id INT \kw{PRIMARY KEY},\\
\ind nombre VARCHAR(100) \kw{NOT NULL UNIQUE},\\
\ind duracion INT \kw{NOT NULL CHECK} (duracion > 0),\\
\ind precio DECIMAL(8,2) \kw{NOT NULL CHECK} (precio > 0),\\
\ind orden INT \kw{NOT NULL}\\
);\\[4pt]
\kw{CREATE TABLE} cita (\\
\ind id INT \kw{PRIMARY KEY},\\
\ind fecha\_hora DATETIME \kw{NOT NULL},\\
\ind estado VARCHAR(20) \kw{NOT NULL DEFAULT} 'programada'\\
\ind\ind \kw{CHECK} (estado \kw{IN} ('programada', 'completada',\\
\ind\ind \hspace*{4.6em}'cancelada')),\\
\ind \ldots\\
\ind \kw{FOREIGN KEY} (servicio\_id) \kw{REFERENCES} servicio(id),\\
\ind \kw{UNIQUE} (empleado\_id, fecha\_hora)\\
);
\end{sqlcode}
\column{.40\textwidth}
\small
\begin{itemize}\setlength\itemsep{6pt}
  \item Tablas, columnas, \textbf{PK}, \textbf{FK} y reglas, escritas como \texttt{CREATE TABLE}.
  \item Como el gestor se conoce, ya se usan sus tipos: \texttt{INT}, \texttt{VARCHAR}, \texttt{DECIMAL}, \texttt{DATETIME}.
  \item Se puede \textbf{ejecutar} en MySQL para probarlo.
\end{itemize}
\vspace{0.15cm}
\footnotesize\color{utpGris} Archivo: \texttt{3\_modelo\_logico.sql}
\end{columns}
\end{frame}

\begin{frame}{Flujo B: el físico completa al lógico}
\begin{columns}[c,onlytextwidth]
\column{.6\textwidth}
\begin{sqlcode}[\dimexpr\textwidth-2\fboxsep\relax]
\scriptsize
\nuevo{\kw{CREATE DATABASE IF NOT EXISTS} peluqueria}\\
\ind \nuevo{\kw{CHARACTER SET} utf8mb4 \kw{COLLATE} utf8mb4\_0900\_ai\_ci;}\\[4pt]
\kw{CREATE TABLE} \nuevo{\kw{IF NOT EXISTS}} servicio (\\
\ind id INT \nuevo{UNSIGNED AUTO\_INCREMENT} \kw{PRIMARY KEY},\\
\ind nombre VARCHAR(100) \kw{NOT NULL UNIQUE},\\
\ind duracion \nuevo{SMALLINT UNSIGNED} \kw{NOT NULL CHECK} (duracion > 0),\\
\ind precio DECIMAL(8,2) \kw{NOT NULL CHECK} (precio > 0),\\
\ind orden INT \nuevo{UNSIGNED} \kw{NOT NULL}\\
) \nuevo{\kw{ENGINE} = InnoDB};\\[4pt]
\com{en cita, el estado pasa a ser un ENUM}\\
estado \nuevo{ENUM('programada', 'completada', 'cancelada')}\\
\ind \kw{NOT NULL DEFAULT} 'programada'
\end{sqlcode}
\column{.36\textwidth}
\small
\begin{itemize}\setlength\itemsep{5pt}
  \item Es el \textbf{mismo diseño}, con lo que \textbf{solo MySQL} tiene.
  \item \texttt{AUTO\_INCREMENT}: MySQL numera el \texttt{id}.
  \item \texttt{InnoDB}: el motor que respeta las FK.
  \item \texttt{utf8mb4}: tildes, ñ y emojis.
  \item \texttt{ENUM}: solo acepta los valores de la lista.
\end{itemize}
\vspace{0.1cm}
\footnotesize\color{utpGris} Archivo: \texttt{4\_modelo\_fisico.sql}
\end{columns}
\end{frame}

\seccion[0]{Forward y Reverse}
% Fuentes: https://dev.mysql.com/doc/workbench/en/wb-forward-engineering.html
\begin{frame}{Forward Engineering: del modelo a la base de datos}
\concepto{Ingeniería directa}{\small En español: \textbf{ingeniería directa} (también «ingeniería hacia adelante»). Parte de un \textbf{modelo} y genera el SQL que crea la estructura de la base. Puede exportar un script o ejecutarlo en un servidor.}
\vspace{0.2cm}
\begin{enumerate}\setlength\itemsep{5pt}
  \item Definir tablas, tipos, claves y restricciones en el modelo.
  \item Generar y revisar las instrucciones \texttt{CREATE TABLE} y los demás objetos.
  \item Ejecutar el script para crear la estructura de la base de datos.
\end{enumerate}
\vspace{0.2cm}
\enlarealidad{En el flujo A, \texttt{dbml2sql} o el botón \textit{Export} de dbdiagram.io hacen ingeniería directa. En MySQL Workbench, la opción \textit{Forward Engineer} genera el script desde su diagrama y lo ejecuta en MySQL.}
\vspace{0.15cm}
\small Crea las tablas \textbf{vacías}: no llena los datos de clientes o citas.
\end{frame}
% Fuentes: https://dev.mysql.com/doc/workbench/en/wb-reverse-engineering.html
\begin{frame}{Reverse Engineering: de la base de datos al modelo}
\concepto{Ingeniería inversa}{\small En español: \textbf{ingeniería inversa}. Parte de una \textbf{base de datos existente} o de su script de creación y reconstruye un modelo de su estructura.}
\vspace{0.05cm}
\begin{enumerate}\setlength\itemsep{2pt}
  \item Leer las tablas, columnas, claves y restricciones existentes.
  \item Importarlas en una herramienta de modelado.
  \item Revisar el modelo obtenido para documentar o modificar la base.
\end{enumerate}
\vspace{0.15cm}
\enlarealidad{\texttt{sql2dbml} y el \textit{Import} de dbdiagram.io convierten un script SQL en DBML. MySQL Workbench tiene \textit{Reverse Engineer}. En SQLite, \texttt{.schema} o DB Browser muestran los \texttt{CREATE TABLE} de un archivo \texttt{.db}.}
\vspace{0.1cm}
\ojo{Recupera solo lo que está \textbf{declarado}. Al pasar el SQL de MySQL por \texttt{sql2dbml}, la relación 1 a 1 entre cita y pago vuelve como 1 a muchos, y los verbos desaparecen.}
\end{frame}
% ---------------------------------------------------------------------

\seccion{Práctica}
\begin{frame}{\ins{Práctica} Un mismo lógico, tres gestores}
\small Partimos del lógico del flujo A: \texttt{proyecto\_mascotas\_flujo\_sin\_gestor/modelado/3\_modelo\_logico.dbml}.
\vspace{0.3cm}
\begin{description}\setlength\itemsep{12pt}
  \item[\etiqueta{SQL Server}] En \textbf{SSMS}, ejecuta \texttt{4\_modelo\_fisico\_sqlserver.sql} y revisa las tablas creadas.
  \item[\etiqueta{MySQL}] En \textbf{MySQL Workbench}, ejecuta \texttt{4\_modelo\_fisico\_mysql.sql}. Luego usa \textit{Reverse Engineer} para ver el diagrama EER.
  \item[\etiqueta{SQLite}] Escribe el físico \textbf{a mano} a partir del lógico y ábrelo en \textbf{DB Browser for SQLite}.
\end{description}
\vspace{0.3cm}
\pregunta{\small ¿Qué cambió entre los tres scripts y qué se mantuvo igual?}
\end{frame}

\begin{frame}{¿Por qué esto es pasar del lógico al físico?}
\begin{columns}[T,onlytextwidth]
\column{.47\textwidth}
\small\textbf{Lo que no cambió en los tres}
\vspace{0.1cm}
\begin{itemize}\setlength\itemsep{5pt}
  \item Las mismas tablas y columnas.
  \item Las mismas PK, FK y reglas.
  \item Es decir, \textbf{el modelo lógico}.
\end{itemize}
\column{.49\textwidth}
\small\textbf{Lo que sí cambió}
\vspace{0.1cm}
\begin{itemize}\setlength\itemsep{5pt}
  \item Cómo se numera el \texttt{id}.
  \item Qué tipo guarda fechas y dinero.
  \item Cómo trata los \texttt{NULL} un \texttt{UNIQUE}, o si revisa las FK.
  \item Es decir, \textbf{el modelo físico}.
\end{itemize}
\end{columns}
\vspace{0.35cm}
\concepto{Del lógico al físico}{\small Pasar del lógico al físico es \textbf{tomar las decisiones de un gestor concreto} sin cambiar el diseño. Cada diferencia que encontraste es una de esas decisiones.}
\vspace{0.1cm}
\small Por eso el flujo A genera un físico distinto por gestor, y en el flujo B el físico se escribe ya para uno solo.
\end{frame}
